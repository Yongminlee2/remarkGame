# 개발일지

끝말잇기(WordChain) 개발 기록. 무엇을 만들었는지보다 **무엇이 문제였고 왜 그렇게 고쳤는지**를 남긴다.

---

## v1.0 — 기본 게임 (2026-07-26)

### 목표
AI와 1:1로 주고받는 한국어 끝말잇기. 완전 오프라인.

### 사전 확보
끝말잇기의 품질은 사전이 8할이다. 공개 데이터를 찾아 CC0 라이선스인
표준국어대사전 추출 명사 목록을 골랐다. 원본이 JS 배열이라 한글 음절(U+AC00~U+D7A3)만
정규식으로 뽑아 **명사 193,050개**를 확보했다.

### 두음법칙
"력"으로 끝나면 "역"으로 시작해도 인정해야 한다. 매핑 테이블을 만들지 않고
**유니코드 음절 분해**로 계산했다.

```
초성 = (코드 - 0xAC00) / 588
중성 = ((코드 - 0xAC00) % 588) / 28
```

초성이 ㄹ이면 중성이 i/y 계열(ㅑㅒㅕㅖㅛㅠㅣ)일 때 ㅇ으로, 아니면 ㄴ으로.
초성이 ㄴ이면 i/y 계열일 때만 ㅇ으로. 단방향이다 — 역→력은 인정하지 않는다.

### 발견한 버그: 사전 불일치
상용 명사 목록(AI가 쓰는 풀)에만 있고 검증용 전체 목록에는 없는 단어가 **230개** 있었다.
"고속도로", "고등학교" 같은 합성어들. 그대로 뒀으면 AI가 낸 단어를 플레이어가 따라 쓸 때
"사전에 없는 단어"로 거부당하는 황당한 상황이 났을 것이다. 두 목록을 합쳐 해결.

### 검증
난이도별 150판씩 데스크톱 시뮬레이션(무작위 유효단어 플레이어)을 돌려
AI 규칙 위반 0건, 시작 단어 843종의 다양성을 확인하고 출시.

## v1.1 — 사운드·음성·사전 확장

### 사전 2배 확장
끄투 계열 게임이 쓰는 오픈소스 DB(`db.sql`, 42MB)에서 `kkutu_ko` 테이블을 추출해
**428,326단어**를 얻었다. 기존 사전과 합쳐 **429,961단어**.
같은 DB의 뜻풀이(`mean`) 컬럼은 placeholder라 쓸 수 없어 이때는 포기했다.

### 효과음·BGM을 코드로 합성
외부 음원을 쓰면 라이선스가 걸린다. 그래서 **전부 코드로 합성**했다.

- 효과음 6종: 사인파 + 배음 + 엔벨로프 조합, 16bit PCM WAV 직접 출력
- BGM: 처음엔 1곡이었는데 요구가 "20곡 랜덤"으로 커져 파라메트릭 제너레이터로 전환

BGM 생성 파라미터:

| 축 | 값 |
|---|---|
| 스타일 | 패드 / 플럭 / 오르골 / 마림바 / 베이스그루브 (5) |
| 코드 진행 | 자연단조 7종 |
| 조성 | ±6 반음 |
| 템포 | 70~109 BPM |

시드 고정 난수로 조합해 20곡 생성, libvorbis q2 인코딩으로 **전곡 합쳐 1.6MB**.
루프 이음새는 앞뒤 60ms 크로스페이드로 처리.

### 음성 입력
`SpeechRecognizer` ko-KR. 인식 결과에서 한글만 남기고(`[^가-힣]` 제거) 자동 제출.

## v1.2 — 상점·뜻풀이·난이도 개편

### 뜻풀이 35만 건
표준국어대사전 기반 공개 JSON 2개(합계 120MB)에서 뜻을 추출했다.
HTML 태그·품사 표기·발음 기호를 정규식으로 걷어내고 첫 문장 위주로 60자에서 잘랐다.

메모리에 30MB를 올릴 수는 없으니 **오프셋 파일 방식**으로 저장했다:

```
means.bin  뜻풀이 원문을 UTF-8로 연달아 붙임 (구분자 없음)
means.idx  단어 i의 뜻 = means.bin[idx[i] .. idx[i+1]]  (4바이트 LE × n+1)
```

사전 순서와 인덱스가 1:1로 대응하므로, 단어를 이진 탐색으로 찾으면
그 인덱스로 바로 뜻의 위치를 안다. 첫 실행 때 `filesDir`로 복사한 뒤
`RandomAccessFile`로 필요할 때만 읽는다. **커버리지 82%.**

### 사전 자료구조 교체
43만 단어를 `HashSet`으로 들면 메모리도 크고 "특정 글자로 시작하는 단어" 조회가 안 된다.
**정렬된 String 배열 + 이진 탐색**으로 바꿨다.

- 단어 검증: O(log n)
- 첫 글자별 후보 조회: lower bound 두 번으로 범위를 구함
- 뜻풀이 인덱스와 순서가 일치

전제 조건이 하나 붙는다 — `dict_all.txt`는 반드시 **LC_ALL=C 정렬**이어야 한다.

### 난이도와 제한시간 분리
"무제한 모드"를 난이도의 한 종류로 넣었더니 "무제한이면서 어려움"을 못 골랐다.
난이도(4단계)와 제한시간 유무를 **직교하는 두 옵션**으로 분리했다.
그러면서 **매우쉬움**을 신설하고, 이 난이도는 한방단어를 절대 쓰지 않도록 못박았다.

## v1.3 — 성장·수집·도전·습관 (대형 확장)

### 설계 원칙: 네 시스템을 따로 만들지 않는다

"레벨도 넣고 아바타도 넣고 미션도 넣자"로 접근하면 서로 무관한 기능 네 개가 된다.
대신 **하나의 순환 고리**로 묶었다.

```
일일 미션이 오늘 할 일을 준다
  → 모험·보스에 도전한다
    → XP·코인을 얻는다
      → 레벨이 오른다
        → 아바타가 해금된다
          → 도감을 채우러 다시 도전한다
```

핵심 결정은 **아바타를 코인으로만 다 모을 수 없게** 만든 것이다.
획득 경로를 넷으로 쪼갰다: 일반 24개는 코인, 희귀 12개는 레벨 달성,
영웅 8개는 보스 클리어, 전설 4개는 도전과제. 그래야 네 시스템이 서로를 필요로 한다.

### 콘텐츠 제작량을 0으로

스테이지를 손으로 만들면 50개를 만들어도 언젠가 끝난다.
**스테이지 번호의 함수**로 난이도를 계산하게 했다.

| 파라미터 | 계산식 |
|---|---|
| 제한시간 | `max(8, 30 - n/3)` — 30초에서 시작해 66스테이지에 8초 |
| 목표 라운드 | `3 + n/3` |
| AI 레벨 | n≤5 매우쉬움 / ≤15 쉬움 / ≤30 보통 / 31+ 어려움 |
| 한방단어 허용 | `n >= 31` |

보스는 5스테이지마다. 25까지는 지정 보스(세글자 도깨비·받침 지킴이·시간 도둑·한방 마왕·긴말 여왕),
30 이상은 **규칙 2개를 조합**한다. 조합은 스테이지 번호를 시드로 뽑아
같은 스테이지면 언제 도전해도 같은 규칙이 나온다. 이걸로 무한히 이어진다.

### 화면과 로직을 분리

새 기능을 전부 Activity에 넣으면 손댈 수 없는 파일이 된다.
난이도 곡선·보스 규칙·아바타 카탈로그·미션·보상 계산을
**Android 의존이 없는 순수 Kotlin**으로 뺐다.

덕분에 위험한 부분을 전부 단위 테스트로 덮을 수 있었다 — **JUnit 73개**.
화면은 그 결과를 그리기만 한다.

### 조합형 아바타

그림을 직접 그리는 대신 CC0 게임 아트 팩을 썼다. 단순한 캐릭터 세트가 아니라
**몸통·눈·입 파츠**라서, 몸 4형태 × 색 6종 × 표정 2세트 = **48종**을 조합으로 만들었다.
이름도 규칙으로 생성한다: `{표정} {색} {형태}` → "방긋 파랑 네모".

## v1.3에서 잡은 버그

전부 리뷰·테스트·계산으로 잡았다. 순서는 심각한 것부터.

### 1. 매우쉬움에서도 플레이어가 즉사 (Critical)

`followUpCount`는 "이 단어 뒤에 이을 수 있는 단어가 몇 개인가"를 세는 함수로,
AI가 "이 단어를 내면 플레이어가 막히지 않는다"를 판단하는 근거다.
그런데 이 함수가 **보스 규칙을 몰랐다.**

보스가 "4글자 이상만" 규칙을 걸면, 어떤 단어는 뒤에 이을 단어가 8개나 있어도
그중 4글자 이상은 0개일 수 있다. AI는 "안전"으로 판단해 그 단어를 낸다.
플레이어는 아무 잘못 없이 즉사한다. **매우쉬움은 한방단어를 절대 안 쓴다**는 약속이 깨진다.

→ `followUpCount`가 보스 규칙을 통과하는 단어만 세도록 수정.
규칙이 없을 때는 조건이 단락 평가로 사라져 자유 대전 동작은 비트 단위로 동일하다.

### 2. 아바타가 외눈으로 렌더링

에셋의 눈 파일이 **눈 한 짝**짜리인 걸 모르고 얼굴 가운데에 1개만 배치했다.
→ 눈 레이어를 좌우 2개로 나누고, 좌 26% / 우 58% 위치에 대칭 배치.

### 3. 파츠가 몸통을 덮음

몸통 PNG는 80×80인데 얼굴 파츠는 타이트하게 크롭돼 있다(눈 20×20, 입 20×7).
네 레이어를 전부 `MATCH_PARENT` + `FIT_CENTER`로 겹치면 각자 독립적으로 확대돼
눈이 아바타 전체를 덮고 입은 가운데를 가로지른다.

→ 측정된 뷰 크기 기준으로 눈은 폭 0.16·상단 0.34, 입은 폭 0.24·상단 0.60에 배치하고
높이는 각 PNG의 고유 종횡비에서 역산. 겹침이 없는지 네 조합 모두 손으로 계산해 확인.

### 4. 잠긴 아바타가 안 보임

미보유 아바타를 "검은 실루엣"으로 표시했는데, 셀 배경도 근검정(#0D0E1C)이었다.
검정 45% 알파를 그 위에 올리면 채널당 차이가 6~7 — 사실상 빈 상자로 보인다.
다크 테마에서 "검은 실루엣"이 애초에 잘못된 선택이었다.
→ 회청색(#40465F) 불투명으로 교체.

### 5. 출석 보상 파밍 가능

출석 처리를 `onResume`에 넣었는데, 이건 다른 화면에서 돌아올 때마다 실행된다.
날짜 가드가 없으면 홈↔상점을 왕복하며 코인을 무한히 받을 수 있다.
→ `lastKey != todayKey` 가드 안에서 날짜를 **무조건 먼저 기록**하도록 수정.

### 6. 레벨 99 이후 XP바 오버플로

레벨은 99에서 멈추는데 `xpIntoLevel`은 계속 증가한다.
만렙 후 한 판만 더 해도 진행률이 100%를 넘고 "N / 12405 XP"가 무한히 커진다.
→ 만렙이면 진행률 고정 + "MAX" 표시.

### 7. 일일 미션이 자주 반복 — 오진을 바로잡은 사례

리뷰에서 "시드 품질이 나쁘다"는 진단이 나왔다. 10년치 시뮬레이션 결과
연속일 중복 3.3%, 7일 창 내 중복 43%라는 데이터까지 붙어 있었다.

그런데 계산해보니 미션 7개 중 3개 조합은 **35가지뿐**이고,
완전 무작위여도 연속일 중복은 1/35 = 2.9%, 7일 창은 45%가 나온다.
**측정값이 무작위 기대치와 일치했다** — 시드는 정상이었고 진짜 원인은 조합 수 부족이었다.

→ 시드를 건드리지 않고, 전날과 같은 조합이 나오면 재추첨하는 방식으로 수정.
제안된 대체 시드(날짜 문자열을 숫자로 변환)도 같은 결함이 있어 채택하지 않았다.

## v1.3.1 — 안드로이드 15+ edge-to-edge 대응

### 증상
새 폰(갤럭시 S24+, 안드로이드 16)에서 화면 맨 아래가 홈버튼 바에 가렸다.
예전 폰(S20 Ultra)에서는 멀쩡했다.

### 원인
`targetSdk 35`(안드로이드 15)부터 시스템이 **edge-to-edge를 강제**한다.
앱이 상태바·내비게이션바 영역까지 그리게 되고,
테마의 `android:statusBarColor` / `android:navigationBarColor`는 **무시된다.**
우리 앱에는 인셋 처리 코드가 하나도 없었다.
예전 폰이 멀쩡했던 건 그 폰이 안드로이드 15 미만이라 강제 대상이 아니었기 때문이다.

### 수정
`ViewCompat.setOnApplyWindowInsetsListener`로 시스템 바 높이만큼
루트 뷰에 패딩을 주는 확장 함수를 만들어 5개 화면 전부에 적용.
게임 화면만 **키보드 인셋까지 포함**시켰다 — 단어 입력창이 키보드에 가리면 안 되니까.

## v1.3.2 — 힌트 개편과 시작 아이템

### 힌트가 단어 3개를 추천
1개만 알려주던 힌트를 3개로 늘렸다. 아무거나 3개가 아니라
**뒤가 막히지 않는 상용 단어를 우선**으로 채우고 모자라면 사전 전체에서 보충한다.
보스전에서는 그 보스의 규칙을 통과하는 단어만 추천한다.

### 시작 아이템 지급
"항상 무료로 3개를 띄우면" 힌트 아이템과 코인 경제가 통째로 무의미해진다.
대신 **시작할 때 아이템을 지급**하는 방식을 택했다 — 사실상 마음껏 쓰면서도 구조는 남는다.

지급량은 요청에 따라 몇 번 바뀌었다(힌트 50개 → 힌트 3000개 → 아이템 5종 각 3개).
지급 플래그에 버전을 붙여서(`starter_granted_v3`) 지급 내용을 바꿀 때마다
이미 받은 사람도 새로 받게 했다. 현재는 `ITEMS` 목록을 순회하며 지급하므로
나중에 아이템을 추가해도 자동으로 함께 지급된다.

## 이어가기 방식 조건 (앱 v1.3.1)

### 문제
"일반 스테이지가 자유 대전이랑 다를 게 없다."
보스에만 규칙이 있고 나머지는 난이도만 오르는 구조였다.

### 조건 축을 둘로 나눔
단어 자체를 제한하는 규칙(글자 수·받침)만으로는 금방 단조로워진다.
그래서 **이어가는 방식**을 바꾸는 축을 새로 만들었다.

| 방식 | 규칙 | 예시 |
|---|---|---|
| 끝말잇기 | 앞 단어의 끝 글자로 시작 | 사과 → 과일 |
| 같은 글자로 계속 | 앞 단어의 첫 글자로 시작 | 사과 → 사람 → 사탕 |
| 앞 글자로 끝내기 | 앞 단어의 첫 글자로 **끝남** | 사과 → 감사 |

두 축은 **겹쳐 걸지 않는다.** "네 글자만 + 거꾸로 잇기"처럼 겹치면 난이도가
곱해져 손쓸 수가 없어진다. 한 스테이지에는 둘 중 하나만 건다.

### 사전 자료구조를 건드려야 했던 이유
사전은 단어 순으로 정렬돼 있어 "○로 시작하는 단어"는 이진 탐색 범위로 바로 나온다.
그런데 앞말잇기는 "○로 **끝나는** 단어"가 필요하다. 정렬 순서로는 답이 안 나온다.

→ 끝 글자 역색인을 추가했다. 43만 단어를 한 번 훑어야 해서
**처음 필요할 때 한 번만** 만들고, 두 번 세는 방식(개수 집계 → `IntArray` 채우기)으로
`Integer` 박싱을 피했다. 사전 로딩이 끝난 시점에 백그라운드로 미리 준비시켜
입력 중 멈춤도 없앴다.

### 세 곳을 전부 갈아끼워야 한다
이어가기 방식은 **단어 검증**·**AI 후보 탐색**·**한방단어 판정** 세 곳에 모두 걸린다.
한 곳만 놓치면 플레이어가 규칙대로 냈는데 지는 버그가 난다.
(v1.3에서 보스 규칙으로 똑같은 실수를 한 적이 있다 — 위 "잡은 버그" 표 참고.)

### 안전성 실측
`tools/ChainSafetySim.java` 로 43만 단어를 전수 검사해
"다음 차례가 아예 막히는" 비율을 쟀다.

| 방식 | 막힘 비율 |
|---|---|
| 끝말잇기 | 0.40% |
| 같은 글자 | 0.00% |
| 앞말잇기 | 1.40% |

앞말잇기가 제일 높지만 쓸 만한 수준이고, AI의 후속 단어 계산도 방식별로
갈아끼워서 낮은 난이도에서는 플레이어에게 막다른 단어를 넘기지 않는다.

## 뜻풀이 전면 보강 (앱 v1.3.1 → v1.3.2)

### 문제 1 — 뜻이 안 뜨는 단어
"표준국어대사전에 없는 단어는 뜻이 안 나온다."
세어 보니 43만 중 **7.7만(18%)** 이 빈칸이었다. 대부분 파생어다 —
'가가대소'는 실려 있는데 '가가대소하다'는 없는 식.

### 문제 2 — 흔한 단어에 엉뚱한 뜻
"사과를 냈는데 뜻이 '잘못을 용서함'이라고 뜬다."
사과만이 아니었다. 관리=菅履(엄짚신), 가계=家鷄(집닭), 만화=萬貨, 기사=騎射, 연기=連記.

### 원인을 확인하는 데 시간을 쓴 것이 남았다
처음엔 파서를 의심했다. 소스를 다시 받아 **원본 레코드를 직접 열어 보고서야**
데이터셋 자체가 표제어당 뜻을 하나만 담고 있고, 동음이의어가 여러 줄로
나뉘어 있지도 않다는 걸 알았다. 파서를 아무리 고쳐도 없는 뜻은 못 만든다.

같은 방법으로 두 번째 막다른 길도 확인했다 — 단어 목록을 가져온 끄투 공개 덤프의
`mean` 칸은 **전부 자리표(`＂1＂［1］（1）`)로 비어 있다.** 저작권 때문으로 보인다.
다만 `type`(품사)·`theme`(분야) 칸은 살아 있어서 나중에 요긴하게 썼다.

### 해결 — 소스를 바꿨다
국립국어원이 stdict.korean.go.kr 로 배포하는 표준국어대사전 XML
(43만 항목, 87개 파일, CC BY-SA 2.0 KR). 여기엔 동음이의어가 `<item>` 으로
전부 들어 있어 **고를 수 있다**는 게 핵심이다.

빈도 수치는 없으므로 사전이 남긴 흔적으로 가늠했다:

| 신호 | 뜻 |
|---|---|
| 용례 개수 | 흔히 쓰는 말일수록 예문이 달린다 (강한 양) |
| 방언·옛말·북한어 | 대표 뜻이 아니다 (강한 음) |
| 전문 분야 전용 | 일상어보다 덜 흔하다 (약한 음) |
| 뜻 갈래 수 | 두루 쓰이는 말일수록 뜻이 갈린다 (양) |
| `=`·`→` 넘겨보기 | 그 자체로는 설명이 안 된다 (음) |

**용례는 개수만 세고 본문에는 싣지 않는다.** 문학작품·기사에서 따온 것이 섞여 있어
사전 본문과 저작권이 따로 놀기 때문이다. 기존 데이터에 박혀 있던 `❖예문 …` 도 걷어냈다.

### 그래도 남는 빈칸은 규칙으로
소스 둘을 우선순위로 합쳐 실제 사전 뜻 **96.2%** 를 확보하고, 남은 3.8%는
어근에서 조립했다. 8단 사다리로 내려가며, 위쪽이 실패할 때만 아래로 간다:

1. 접미사 파생 — 어근 뜻을 살린다 (`-하다`/`-되다`/`-거리다`/`-히` …)
2. 이름씨 꼬리 — `-적`/`-학`/`-자` 처럼 뜻이 정해진 꼬리
3. 합성어 — 양쪽으로 갈라 둘 다 뜻이 있으면 이어 붙인다
4. 한자만 아는 경우 — 어근 설명은 없어도 한자 표기는 알려 준다
5. 거꾸로 파생 — '가느슥'처럼 어근만 표제어로 오른 말은 `-하다` 형을 가리킨다
6. 작품 이름 — 끄투 분야 꼬리표로 "《디지몬》에 나오는 이름"
7. 품사·분야 꼬리표 — "부사." "《화학》 분야의 명사."
8. 그래도 모르면 — **모른다고 밝힌다**

**없는 뜻은 지어내지 않는다**가 원칙이다. 자동 생성분이라는 사실은 앱 정보 화면에 적었다.

### 파이프라인으로 정리
한 번 하고 끝날 일이 아니라 4단계로 나눠 언제든 다시 만들 수 있게 했다.

```
extract_stdict.py      표준국어대사전 XML → 동음이의어 중 흔한 뜻 고르기
extract_kkutu_meta.py  끄투 낱말표 → 품사·분야 꼬리표
build_means.py         소스 tsv 들을 우선순위대로 합쳐 means.bin/idx 생성
gen_means.py --write   남은 빈칸을 어근에서 규칙으로 채우기
```

### 자산 세 파일을 테스트로 묶었다
`dict_all.txt`·`means.bin`·`means.idx`는 i번째 단어의 뜻이
`means.bin[idx[i]..idx[i+1]]` 이라는 약속으로 이어져 있다.
하나만 다시 만들고 나머지를 안 맞추면 **모든 단어가 엉뚱한 뜻을 달게 되는데**,
화면에서는 그냥 "이상한 뜻"으로 보여서 알아채기 어렵다.

→ `MeansAssetTest` 5개로 고정했다. 항목 수 일치, 오프셋이 0에서 시작해
파일 크기로 끝남, 오프셋 역전 없음, 빈 뜻 없음, UTF-8 무결성.
안드로이드 없이 파일을 직접 읽으므로 JVM 단위 테스트에서 돈다.

### 결과

| | 전 | 후 |
|---|---|---|
| 실제 사전 뜻 | 82% | **96.2%** |
| 규칙 생성분 | 18% | **3.8%** |
| 뜻 없는 단어 | 77,191개 | **0개** |
| means.bin | 30MB | 37MB |

## 조작 다듬기 (앱 v1.3.2)

### 항복했는데 부활을 묻는다
항복은 스스로 그만두는 것인데 부활 아이템을 권하고 있었다.
원인은 종료 사유를 **문자열로 판별**하고 있었기 때문 —
`reason.contains("한방단어")` 로만 걸러서 "항복했어요"는 그물을 빠져나갔다.

→ 명시적 인자(`canRevive`)로 바꿔 '져서 끝났을 때'와 '스스로 그만둔 때'를 갈랐다.
문자열 판별은 조건이 늘어날 때마다 조용히 새는 종류의 코드다.

### 스테이지 조건이 눈에 안 들어온다
"4글자 이상 같은 조건이 처음엔 뭔지 몰랐다."
모험 화면에서 조건이 본문과 같은 14sp 로 조용히 놓여 있었다.

→ 19sp 로 키우고 배경 판과 색 테두리를 넣었다(보스는 빨강, 일반은 노랑).
게임 화면 배너와 같은 모양으로 맞춰 두 화면에서 같은 것으로 읽히게 했다.

### 만든이·버전 정보
문의가 들어왔을 때 어느 빌드인지 알 수 없으면 재현부터 막힌다.
정보 화면에 만든이·메일·저장소 주소와 함께 **버전 이름 + 빌드 번호**를 넣고,
메일 링크를 누르면 제목에 버전이 자동으로 들어가게 했다.

데스크톱 하네스(`tools/`)로 곡선을 실제로 측정했다.

### 레벨 곡선

| 목표 | 기준 | 실측 | 판정 |
|---|---|---|---|
| 레벨 10 | 15판 이내 | 17판 | 미달 |

| 레벨 50 | 200판 이내 | 127판 | 통과 |

그때 `ProgressTest`의 기대값도 함께 고쳐야 한다.

### 보스 규칙 안전성

사전 전체를 훑어 "규칙을 통과하는 단어가 하나도 없는 시작 글자"를 셌다.

| 규칙 | 후보 0인 시작 글자 | 비율 | 단어량 기준 |
|---|---|---|---|
| 3글자 이상 | 274 / 2,090 | 13.1% | 0.09% |
| 받침으로 끝남 | 387 / 2,090 | 18.5% | 0.17% |
| 4글자 이상 | 496 / 2,090 | 23.7% | 0.23% |

글자 수 기준으로는 높아 보이지만 해당 음절이 전부 희귀·고어라
**실제 단어량 기준으로는 0.25% 미만**이다. 게다가 후보가 0이면
플레이어 패배가 아니라 AI 항복으로 처리되므로 규칙 완화는 하지 않았다.

## 개발 환경에서 겪은 문제

### 한글 사용자 경로에서 단위 테스트가 죽는다

```
ClassNotFoundException: worker.org.gradle.process.internal.worker.GradleWorkerMain
```

Gradle 테스트 워커 JVM이 클래스패스를 못 읽어 죽었다.
원인은 Gradle 배포본이 `C:\Users\사용자\.gradle\...` 아래에 있고
그 경로에 **한글이 들어 있어서**였다. 워커 프로세스에 클래스패스를 넘길 때
경로 인코딩이 깨진다.

→ Gradle 홈을 ASCII 경로로 복사하고 `GRADLE_USER_HOME=C:/gradle-home`을 붙여 실행.
빌드(`assembleDebug`)는 이 변수 없이도 동작한다.

또 하나 배운 것: **`BUILD SUCCESSFUL`은 테스트가 돌았다는 증거가 아니다.**
테스트가 0개 실행돼도 성공으로 나온다.
`app/build/test-results/testDebugUnitTest/*.xml`의 `tests=` / `failures=`를 봐야 한다.

  '수도'는 首都가 아니라 水道가 뽑힌다. 기준을 조이거나 예외 목록을 두면 되지만
  지금은 눈에 띄는 오선택이 거의 없어 두고 있다.
- 플레이스토어 제출 준비: 512×512 아이콘 PNG, 1024×500 피처 그래픽,
  스크린샷, 스토어 설명(단문 80자·장문 4000자), 키스토어 생성 후 AAB 빌드
